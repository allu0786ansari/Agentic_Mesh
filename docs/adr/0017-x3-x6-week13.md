# ADR 0017 — X3 fusion, X4 attribution, X5 latency, X6 chaos, robustness (Week 13)

**Status:** Accepted, 19 October 2026. Written before any X3, X4, X5, X6 or robustness
result is computed.

**Implements:** Plan Week 13, tasks 1–5; Proposal §10.5–10.7; H2a–H2c; PT4, PT5
(validation part) and PT7.

**Builds on:**

- ADR 0009: edge runtime and fusion (Δt = 60 s, k = 2, latency-only excluded; not
  tuned);
- ADRs 0012–0015: mesh, LLM path and G3;
- ADR 0016: the X1 headline model.

**Scope:** validation only. Every test-split number (PT4 on test time, PT5 on the 35
HAI test events) is computed once after `g4-frozen`, with the same code.

## 1. Models

The **headline model** is FedProx μ = 0.01 at ε = 3, as in ADR 0009 and ADR 0016.

**Five seeds** (11, 23, 37, 41, 53) are used, not only the deployed seed 11.

- **Retraining:** each seed is retrained with `--save-model` into
  `results/models/<config>/seed_<n>`.
- **Run:** on the laptop, one per process (`make x3-models`, about 75 min for both
  sites).
- **Reproducibility check:** each retrained artifact must reproduce its X1 artifact
  (same metrics to 1e-9) before it is used. A mismatch stops X3 and is reported.

**Scoring** uses the edge runtime's own path:

- calibrators and thresholds per node at 1% FPR on normal validation, as in ADR
  0009;
- R0 on Site B, R3 on Site A;
- scoring is causal and batch-equivalent.

## 2. X3 — fusion on Site B (RQ2)

**Detectors.** All three use the same per-node alerts at the same per-node
thresholds:

| Detector | Alarm |
|---|---|
| single node *n* | an incident built from node *n*'s alerts alone (the same Δt = 60 s chaining), so every detector counts incidents, not windows |
| 2-of-3 | an incident whose counting alerts come from at least 2 distinct nodes |
| noisy-OR | an incident whose noisy-OR score is at least τ |

**τ for noisy-OR (matched FPR).** This is the protocol ADR 0009 §7 deferred to
here.

- **The rule:** τ is the smallest observed incident noisy-OR value at which
  noisy-OR's benign false alarms per hour do not exceed the best single node's.
- **Data and seeds:** it is set on Site B normal validation, per seed.
- **What is not used:** τ uses no attack data.

**Metrics:**

- **H2a:** false alarms per hour, on benign validation time (normal validation of
  all three nodes, the same hours).
  - "Best single node" means the node with the **fewest** benign false alarms per
    hour (the strongest comparator).
  - **PT4:** 2-of-3 reduces false alarms per hour by at least 30% against it. The
    one-sided test is H1: reduction > 0.30, with B = 10 000 block-bootstrap draws
    over 60 min benign blocks, paired across detectors, seeds averaged.
  - The claim is made on test time after G4; validation is development evidence.
- **H2b:** event recall per episode on the real attack day (validation episodes
  0–3), with time to detect.
  - The single-node reference is **b1 (IED1A)**, the only node that observes the
    attack.
  - The recall loss of 2-of-3 is reported, not hidden. No target.
- **H2c (synthetic):** event recall and time to detect on the labelled synthetic
  multi-device scenario (§3), at the matched τ. It is reported as synthetic,
  everywhere.

**CIs** come from the block bootstrap (benign blocks; episodes or synthetic events),
paired, with seeds averaged inside each draw.

## 3. X3 synthetic scenario (`experiments/x3_synthetic.py`)

**What is injected.** A **cross-device write burst** is placed into the benign
normal-validation stream of two devices at the same time.

- **Count and spacing:** 24 bursts with a fixed seed (2026). They are at least
  30 min apart and rotate over the pairs (b1, b2), (b2, b3), (b1, b3).
- **Duration:** each burst is 6 consecutive 10 s windows (60 s).
- **Content:** in each injected window, `req_write` is set to *W* and `req_recv`
  and `hmi_requests` are raised by *W*. Nothing else changes, and the features are
  recomputed through the same `log1p` and standardisation.
- **Magnitude:** primary *W* = 5. *W* ∈ {3, 10} is reported as sensitivity. Benign
  validation has `req_write` of at most 2 per window.
- **Labels:** each burst is one labelled synthetic event on both devices. Event
  recall uses the 60 s tolerance.
- **Status:** the scenario is fixed now and never tuned. Its results are always
  marked synthetic.

## 4. X4 — attribution, the four modes, on validation incidents (RQ3)

**Inputs.**

- **Runs:** the validation mesh runs already made, all under ADR 0013 §7:
  - `rule_only` and `retrieval_only`, the latest runs;
  - `full`, the Week 11 mTLS runs;
  - `llm_no_retrieval`, the ADR 0013 §7.4 runs.
- **Export:** their per-session records are exported from each run's `storage.db`
  on the laptop to `sessions.jsonl` (`make x4-export`).
- **What a record holds:**
  - the incident window and nodes;
  - the mode used;
  - the technique and its ranked list;
  - the tactics;
  - the LLM's validity and grounding.

**Site A (15 validation events, ground truth `gt-frozen`).**

- **Matching:** an incident matches an event when its window overlaps the event's
  labelled span widened by the 60 s tolerance.
- **The event's attribution:** that of its **earliest** matching incident, which is
  the first one an operator sees. Incidents that match no event are counted as
  false-positive incidents, with no accuracy.
- **Metrics:**
  - technique top-1 and top-3 against the acceptable sets (mapping protocol v1.1,
    revoked-by normalisation; a parent does not match a sub-technique);
  - abstention, and missed events (no incident);
  - tactic accuracy, reported but never used for a claim (constant baseline 1.0);
  - raw grounding rate.
- **Baselines:**
  - the majority-class baseline (the most frequent acceptable technique on the 15
    events);
  - the constant-answer baseline from the frozen mapping (0.64 on all 50 events,
    also reported on these 15).
- **CIs:** bootstrap over events, B = 10 000.
- **The `full`-against-`retrieval_only` comparison** (PT5's second clause) is a
  paired event bootstrap of top-3.

All of this is development evidence. PT5's claim is made on the 35 test events.

**Site B (case study, no accuracy).**

- **Reported per episode:** the chosen technique of the earliest matching incident,
  in each mode.
- **Reported per mode:** JSON validity and raw grounding over all incidents.
- **Checker:** the grounding rate after validation must be 100% (every dispatched
  technique is a candidate), and every mode must be present.

## 5. X5 — latency (PT7)

Latency is reported per segment, as p50 and p95, from the committed run artifacts:

| Segment | Source |
|---|---|
| detection | edge runs |
| investigation | the Week 11 mTLS runs |
| incident-to-dispatch, `retrieval_only` and `full` | the Week 11 mTLS runs |

**Output:** `python -m agmesh.evaluation.latency --report` writes
`results/X5/latency_val.json`.

**Not measured:** replay is back to back, so queueing is not measured (ADR 0013
§3.4).

## 6. X6 — chaos (`tests/chaos/`; EA1)

The tests run against real node API processes over mTLS (ADR 0014) with a scripted
LLM:

1. a node fails before, during and after a hop;
2. a node API process is killed mid-session (SIGKILL);
3. a slow node, beyond the read timeout;
4. the mesh is killed mid-session and restarted, and the session resumes from
   SQLite;
5. a duplicate alert is replayed.

**What must hold:**

- every session reaches a terminal state;
- there are zero duplicate dispatches;
- breaker transitions are logged.

**Output:** a chaos report artifact, `results/X6/chaos.json`, written by
`make chaos`.

## 7. Robustness suite (synthetic, detection only)

**Perturbations.** Four kinds, all labelled synthetic:

| Kind | What it does |
|---|---|
| spike | +6 σ on one feature for one window |
| drift | a linear ramp to +3 σ over 10 min |
| stuck-at | a feature frozen at its last value for 10 min |
| replay | 10 min of earlier windows replayed |

**Where:** they go into normal validation, on both sites, with every node and seed
of the headline model.

- **Counts:** 20 injections per kind and node, with seed 2026.
- **σ:** the feature's training standard deviation.
- **Features:** the feature is drawn uniformly among the node's model inputs.

**Reported:** the detection rate per kind (60 s tolerance) and the window FPR on the
untouched windows. The tables are descriptive; nothing is selected or tuned on them.
